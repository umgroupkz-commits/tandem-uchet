# Подпроект 3 — «Документы склада»

Дата: 5 сентября 2026. Статус: утверждено к реализации.
Родительская спецификация: `2026-09-04-uchet-core-design.md` (3.2 три слоя данных, 3.3 проведение
и отмена, 3.4 себестоимость, 3.5 роли). Опирается на подпроект 2 (`charts`, `item_cost`,
`items.cost_price`).

Реализуется двумя планами: **3а** — данные, проведение, бэк-офис; **3б** — телефонный экран
кладовщика поверх тех же RPC.

## 1. Цель

Складской учёт внутри системы вместо iiko: приход от поставщиков, перемещения между складами,
списания, акты производства по техкартам, инвентаризации. Из документов рождаются движения,
из движений — остатки и средневзвешенная себестоимость по складу. Стартовые остатки каждого
склада задаются его первой инвентаризацией.

Не входит: списание сырья по продажам точек (подпроект 4), оплаты и взаиморасчёты с
поставщиками (подпроект 5), штрихкоды, печатные формы, партии и сроки годности, заявки
поставщикам, импорт исторических документов iiko.

## 2. Решения

- **Движения — источник истины, остатки — производная таблица.** `stock_moves` хранят
  количество со знаком и себестоимость единицы; `stock_balances` держат текущее количество и
  среднюю себестоимость по (склад, позиция), пересчитываются в транзакции проведения и
  восстанавливаются функцией пересборки из движений. Остаток на дату — сумма движений.
- **Средневзвешенная себестоимость по складу** для товаров: при приходе
  `avg = (qty_было × avg_было + qty_прихода × цена) / (qty_было + qty_прихода)`; если остаток
  был ≤ 0 — средняя = цена прихода. Списание, перемещение и расход производства идут по средней
  склада-источника; перемещение приходует на склад-получатель по той же цене, там средняя
  пересчитывается как при приходе. Выпуск производства приходуется по сумме списанного сырья,
  делённой на выпуск.
- **Две цены у товара — сознательно.** `items.cost_price` (учётная, для техкарт и фудкоста) =
  цена последнего проведённого прихода (`cost_source='document'`); `stock_balances.avg_cost` —
  средняя по конкретному складу для движений. Они близки, но не обязаны совпадать.
- **Отрицательный остаток допускается** (контрольный склад): проведение возвращает
  предупреждения, интерфейс просит подтвердить. До первой инвентаризации склад живёт с
  расчётным остатком от нуля.
- **Инвентаризация фиксирует момент**: расчётный остаток берётся на момент проведения
  (текущий `stock_balances`), поэтому инвентаризацию за день проводят последней. Проведённая
  инвентаризация запрещает отмену проведения любого более раннего документа, который двигал
  этот склад (по `posted_at`).
- **Производство раскрывает карту на один уровень.** Ингредиент-полуфабрикат берётся со склада
  как есть; его выпуск — отдельный акт. Строки расхода генерируются при проведении и
  сохраняются в документе (`line_kind='consume'`), редактированию не подлежат — исправляется
  карта.
- **Номера документов** — по типу и году: `ПН-2026-000123` (приход), `ПМ` перемещение, `СП`
  списание, `АП` производство, `ИН` инвентаризация; последовательности в таблице
  `doc_counters(doc_type, year, last_no)`.
- **Время документа** — `doc_date date` плюс порядок проведения `posted_at`; отчёты «на дату»
  включают документы с `doc_date <= дата`.

## 3. Модель данных

```
documents      id uuid PK, doc_type text ('invoice_in'|'transfer'|'writeoff'|'production'|'inventory'),
               number text unique, doc_date date not null default current_date,
               status text ('draft'|'posted') default 'draft',
               store_from uuid null -> stores, store_to uuid null -> stores,
               counteragent_id uuid null -> counteragents,     -- поставщик у прихода
               reason text null,                              -- списание: 'spoilage'|'tasting'|'staff_meals'|'other'
               comment text null, total_sum numeric null,     -- сумма по строкам после проведения
               created_by uuid -> users, created_at timestamptz, updated_by, updated_at,
               posted_by uuid null -> users, posted_at timestamptz null
               check по типу: invoice_in требует store_to и counteragent_id; transfer — оба склада
               и store_from <> store_to; writeoff/inventory/production — store_from
               (у production это склад кухни: и расход, и выпуск на нём)

document_lines id uuid PK, document_id uuid -> documents cascade, line_kind text default 'item'
               ('item' | 'consume'), item_code text -> items, qty numeric not null check (>= 0),
               unit_id text -> units (копия единицы позиции на момент строки),
               price numeric null, sum numeric null,
               fact_qty numeric null, calc_qty numeric null,  -- инвентаризация
               note text null, sort_order int default 0

stock_moves    id bigserial PK, document_id uuid -> documents, line_id uuid -> document_lines,
               store_id uuid -> stores, item_code text -> items, qty numeric not null (со знаком),
               unit_cost numeric not null default 0, move_date date not null,
               posted_at timestamptz not null default now()
               index (store_id, item_code, move_date), (document_id)

stock_balances store_id uuid, item_code text, qty numeric not null default 0,
               avg_cost numeric not null default 0, updated_at timestamptz, PK (store_id, item_code)

doc_counters   doc_type text, year int, last_no int, PK (doc_type, year)

role_permissions + раздел 'stock' (журнал, остатки, движения):
               admin v+e, owner v+e, storekeeper v+e, accountant v+e, technologist v+e
               + разделы по типам документов (право «проводить/отменять»):
               'doc:invoice_in'  — admin, owner, storekeeper, accountant (edit)
               'doc:transfer'    — admin, owner, storekeeper
               'doc:writeoff'    — admin, owner, storekeeper
               'doc:production'  — admin, owner, technologist, storekeeper
               'doc:inventory'   — admin, owner, storekeeper
               (view у всех перечисленных)
```

Все таблицы под RLS без политик, доступ только через RPC. `stores.point_id` уже есть —
экран точки в подпроекте 4 будет списывать с `points.default_store_id`.

## 4. Проведение

`tandem.doc_post(p_doc uuid, p_user tandem.users) → jsonb {ok, warnings:[{item_code, name,
store_id, store_name, balance_after}]}` — одна транзакция:
1. Документ в статусе `draft`; у пользователя право `edit` на раздел `doc:<тип>`.
2. Проверки: склады существуют и активны; позиции активны; `qty > 0` у строк `item`
   (у инвентаризации — `fact_qty >= 0`, хотя бы одна строка); у прихода `price >= 0`; у
   производства — все строки типа `dish`/`prepared` и у каждой есть карта, действующая на
   `doc_date` (иначе `validation` с перечнем).
3. Движения по типу (см. раздел 2); для производства — сначала генерируются строки `consume`
   (брутто × qty / output_amount по каждой строке карты, одинаковые ингредиенты складываются),
   затем движения: минус по ингредиентам, плюс по выпуску с `unit_cost = Σ расход / qty`.
4. Для инвентаризации: `calc_qty` = текущий `stock_balances.qty` (0, если строки нет);
   движение на `fact_qty − calc_qty` с `unit_cost = avg_cost` (если средней нет — `cost_price`
   позиции, иначе 0); строки с нулевой разницей движений не создают.
5. Обновление `stock_balances` в порядке строк; после — список позиций с `qty < 0` среди
   затронутых → `warnings`.
6. Приход: `items.cost_price = price, cost_date = doc_date, cost_source = 'document'` для
   каждой строки.
7. `status='posted'`, `posted_by/posted_at`, `total_sum`, номер выдаётся при первом сохранении
   (черновик уже с номером).

`tandem.doc_unpost(p_doc, p_user)`: документ `posted`; право на тип; нет проведённой
инвентаризации по любому из складов документа с `posted_at` позже (иначе `validation`
«после этого документа проведена инвентаризация № … — сначала отмените её»); движения
удаляются, `stock_balances` пересчитываются для затронутых пар из движений
(`tandem.rebuild_balance(store, item)` проигрывает оставшиеся движения пары в порядке
`posted_at`, применяя ту же формулу средней, что и проведение, — поэтому состояние
восстанавливается точно);
строки `consume` удаляются; у прихода `cost_price` не откатывается (учётная цена — последняя
известная закупка); статус `draft`.

`tandem.rebuild_balances()` — служебная: пересобирает всю `stock_balances` из `stock_moves`
(используется тестом для сверки и при подозрении на расхождение).

Ошибки — `{ok:false, error, message}`; конкурентное проведение одного документа — блокировка
строки документа `for update`.

## 5. RPC (через `tandem_office`, раздел `stock`; префиксы `doc%`, `stock%` → `stock`)

- `docs_list {doc_type?, store_id?, status?, date_from?, date_to?, q?, page?}` → строки: id,
  номер, тип, дата, статус, склады, контрагент, сумма, автор; по 200; `q` — по номеру,
  контрагенту, комментарию.
- `doc_get {id}` → шапка + строки (`item` и `consume` отдельно) + для инвентаризации текущий
  расчётный остаток по каждой строке (подсказка до проведения; после — сохранённый `calc_qty`).
- `doc_save {id?, doc_type, doc_date, store_from?, store_to?, counteragent_id?, reason?,
  comment?, lines:[{item_code, qty|fact_qty, price?, note?}]}` → `{ok, id, number}`; только
  черновики; проверки формы по типу (раздел 3); строки полностью заменяются.
- `doc_post {id}` → как `tandem.doc_post`; при минусах документ **проводится всё равно**
  (решение: допускать), предупреждения возвращаются в ответе; интерфейс показывает их
  заранее через `doc_preview` и просит подтвердить перед вызовом `doc_post`.
- `doc_preview {id}` → `{warnings, consume:[…]}` — что произойдёт при проведении (для
  производства — расход по картам; для всех — позиции, уходящие в минус) без записи.
- `doc_unpost {id}`, `doc_delete {id}` (только `draft`).
- `stock_balances {store_id?, q?, only_nonzero?, page?}` → строки: склад, позиция, единица,
  количество, средняя, сумма; итого по складу; `csv`.
- `stock_moves {store_id?, item_code?, date_from?, date_to?, page?}` → движения с документом.
- `item_stock {code}` → остатки по складам и последние 20 движений (для карточки номенклатуры).
- `stock_rebuild {}` → только `admin`: пересборка остатков, возвращает число расхождений до.

Право: `*_list`, `*_get`, `*_preview`, `stock_balances`, `stock_moves`, `item_stock` → `view`
раздела `stock`; `doc_save/doc_delete` → `edit` раздела `stock` **и** `edit` раздела
`doc:<тип>`; `doc_post/doc_unpost` → `edit` раздела `doc:<тип>`; `stock_rebuild` → роль `admin`.
(Диспетчер проверяет `stock`; проверку `doc:<тип>` делает `office_stock` внутри.)

## 6. Бэк-офис (план 3а)

Раздел «Склад» (`js/office/stock.js`):
- вкладка **Документы**: фильтры (тип, склад, статус, период, поиск), таблица, кнопка «Новый»
  с выбором типа; форма документа: шапка по типу (дата, склады, поставщик, причина,
  комментарий), таблица строк с поиском позиции (`items_search`, только активные; для
  производства — только `dish`/`prepared`), количество (единица позиции), цена и сумма у
  прихода, факт у инвентаризации (с подсказкой расчётного и кнопкой «заполнить позициями с
  остатком»); действия: «Сохранить», «Провести» (перед проведением — `doc_preview`: расход по
  картам и минусы, подтверждение), «Отменить проведение», «Удалить черновик»; проведённый
  документ — только чтение с блоком строк расхода;
- вкладка **Остатки**: склад, поиск, «только с остатком», таблица, итог, CSV; клик по позиции —
  движения по ней на этом складе;
- в карточке номенклатуры (`nomenclature.js`): блок «Остатки по складам» и последние движения.
- Раздел виден ролям с `stock:view`; кнопки действий — по правам типа (ответ `me` уже отдаёт
  список `permissions`, туда попадут и `doc:<тип>:edit`).

## 7. Телефонный экран кладовщика (план 3б)

`stock.html` в стиле экранов точек (крупные элементы, минимум полей): вход логином и PIN
(тот же `office_login`; роль `storekeeper` или любая с `doc:*`), выбор склада (по умолчанию —
склад точки пользователя, если задан; иначе список), три сценария:
- **Приёмка**: поставщик (поиск по контрагентам-поставщикам), позиции (поиск, плитки частых
  по этому складу — из последних приходов), количество и цена, «Провести» → предупреждения
  → готово; черновик сохраняется автоматически, как на экране точки;
- **Инвентаризация**: список позиций склада с ненулевым остатком плюс поиск для добавления;
  поле «факт» крупное; расчётный остаток **не показывается** до проведения (слепой подсчёт);
  «Провести» → сводка расхождений (позиция, разница, сумма) → подтверждение;
- **Перемещение**: склад-куда, позиции, количество, «Провести».
Всё через те же RPC; отдельного бэкенда нет. Детали формы и проверки — в плане 3б.

## 8. Проверка

Дымовой тест, раздел `stock` (тестовые склады `ZZ_TEST_склад А/Б`, позиции ZZ_TEST_мука
(кг), ZZ_TEST_тесто (ПФ, карта: мука 0,5/0,5/0,45, выход 0,45), поставщик ZZ_TEST_ИП):
1. Приход 10 кг по 100 → остаток А: 10, средняя 100; `cost_price` муки = 100, источник
   `document`. Второй приход 10 по 200 → остаток 20, средняя 150.
2. Перемещение 5 кг А→Б → А: 15 (150), Б: 5 (150).
3. Списание 2 кг с А (порча) → А: 13; движение по 150 (сумма 300).
4. Производство 0,9 кг теста на А → расход муки 1 кг по 150 (строка `consume`), выпуск теста
   0,9 по 166,67; А: мука 12, тесто 0,9.
5. `doc_preview` списания 20 кг → предупреждение «уйдёт в минус», проведение допускается;
   отмена проведения возвращает остаток.
6. Инвентаризация А: факт муки 11 при расчёте 12 → движение −1 по 150; после неё
   `doc_unpost` прихода → `validation`; `doc_unpost` инвентаризации → ок, затем прихода → ок,
   остатки пересчитаны.
7. `stock_rebuild` → расхождений 0; повтор всех чисел совпадает.
8. Права: технолог проводит производство, но не приход (`forbidden`); кладовщик проводит приход;
   бухгалтер не проводит списание.
9. Номера: два прихода → `ПН-2026-…` с ростом на 1.
`tandem_test_cleanup` расширяется на `documents` (каскадом строки и движения) и
`stock_balances` тестовых складов/позиций; после прогона `leftovers = 0`.

Регресс: экраны точек и бэк-офис прежних разделов не меняются (полный прогон теста).

## 9. Критерии готовности

1. Кладовщик заводит приход, перемещение, списание и инвентаризацию в бэк-офисе; технолог —
   акт производства; документы проводятся и отменяются по правилам раздела 4.
2. Остатки и средняя себестоимость по складу сходятся с ручным пересчётом на контрольном
   сценарии раздела 8; пересборка из движений даёт те же числа.
3. Стартовая инвентаризация склада «Магазин кухни» проведена Светланой или кладовщиком
   (данные — их; система готова принять).
4. Телефонный экран (3б): приёмка и инвентаризация проходят с телефона за минуты без
   бэк-офиса.
5. Экраны точек не изменились.
