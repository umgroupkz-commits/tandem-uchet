# ИИ-бот приёма заказов «Енешки»

Дата: 16.10.2026. Поручение Светланы Глухих (ТОО «Тандем KZ») от 16.10.2026: UM Group берёт приём заказов.
Решения ниже приняты Андреем в брейншторме 16.10.2026. Предложения, которые ждут Светланы, вынесены
в раздел «Открытые решения Светланы» и в коде становятся настройками, а не константами.

## Цель MVP

Клиент пишет в WhatsApp Енешки. Бот на русском или казахском собирает заказ целиком: позиции из меню,
количество, дату и час, доставку или самовывоз, адрес. Он показывает клиенту итог с суммой и после «да»
кладёт заказ в учёт Тандема. Продавец подтверждает заказ одной кнопкой на планшете кассы или в Telegram,
и только после этого клиент получает «заказ принят», а заказ идёт в план кухни. Дальше клиенту приходят
сообщения о статусах до выдачи; выдача превращается в чек кассы.

На старте каждый заказ подтверждает человек. Автоподтверждения в MVP нет.

## Решения

1. **Бот собирает заказ сам, подтверждает человек.** Бот ведёт разговор до итога, но слово «принят»
   клиенту говорит только после нажатия продавца.
2. **Канал — «Узел»** (свой шлюз WhatsApp, `C:\Вайбкодинг\Альтернатива Wazzup`), а не Wazzup.
   Бот работает по ключу программы с галочкой «Этот ключ — бот»: вебхук с подписью HMAC, текст
   сообщений через `GET /v1/dialogs/<id>/messages`, отправка `POST /v1/messages`, передача человеку
   `POST /v1/dialogs/<id>/handoff`. Продавцы продолжают отвечать с телефона; после ответа человека
   «Узел» сам ставит паузу бота в этом диалоге, вернуть разговор боту может только сотрудник.
3. **Один VPS Тандема** (PS.kz Basic-1, 1 ГБ): учёт (самохостинг из `server/`: прокси `tandem_gate`),
   установка «Узла» и бот, каждый в своём контейнере, и **один общий сервер Postgres 17** с отдельными
   базами для учёта, «Узла» и бота (вторая копия Postgres в 1 ГБ не помещается). Образы собираются
   на машине владельца (`vykatit.sh`), сервер не собирает; на сервере включён swap. Учёт переезжает с Supabase на VPS отдельной работой;
   бот ходит в учёт через `tandem_gate` по адресу из настройки `UCHET_API_URL`, поэтому его можно
   запустить и до переезда (адрес Supabase), и после (адрес прокси во внутренней сети).
4. **Бот живёт рядом с «Узлом»** — Deno/TypeScript, как «Узел» и бот «Полежим?». Своя схема `bot`
   в своей базе общего Postgres хранит только переписку: диалоги, черновики, журнал
   обработанных событий. **Заказ клиента живёт только в учёте** — второй правды нет.
5. **Модель разговора — Claude Sonnet 5.5** (`claude-sonnet-5-5`) по ключу Anthropic в переменной
   окружения VPS. Оценка: около $40–60 в месяц при 40 разговорах в день с кэшем системной части.
   Модель меняется настройкой `BOT_MODEL`.
6. **Цены и суммы считает код, не модель.** Модель работает через инструменты, а инструменты отклоняют
   всё, чего нет в меню, что стоит на стопе или нарушает окно готовности.
7. **Меню ведётся в учёте**, а не в коде бота: раздел бэк-офиса «Меню заказов». У позиции меню
   **своя цена для заказов**, отдельная от цены кассы. Бот видит позицию, только когда цена отмечена
   «сверена», — так устаревшие цены учёта (котлета 1 600 вместо 4 550) к клиенту не попадут.
8. **Карточка подтверждения — в двух местах сразу:** вкладка «Заказы» на планшете кассы и группа
   Telegram «Енешка — заказы». Решает тот, кто нажал первым; второй видит «уже подтвердил(а) …».
9. **Кухня получает и план, и список к часу.** Подтверждённые заказы входят колонкой «Клиенты» в план
   «Склад → Заявки» на свою дату и в акт производства; живой список «Заказы на сегодня» отсортирован
   по сроку «готово к».
10. **Оплата двух видов.** По умолчанию — при получении: «Доставлен»/«Выдан» + способ оплаты (наличные,
    Kaspi QR, перевод, карта) превращает заказ в чек кассы. Продавец может подтвердить заказ
    с предоплатой: бот присылает реквизиты Kaspi из шаблона, на кухню заказ идёт после отметки
    «оплата пришла». Общее правило предоплаты — настройка, по умолчанию выключена.
11. **Языки — русский и казахский.** Ответ на языке клиента. Ключевые фразы (итог, «принят»,
    реквизиты, «в пути», «готов», отказ) — заготовленные шаблоны на двух языках, сверенные заранее;
    модель их не пересказывает.

## Устройство

```
Клиент WhatsApp ──► «Узел» ──вебхук, HMAC──► eneshka-bot (Deno) ──tandem_gate, служебный ключ──► Учёт Тандема
                      ▲                          │  ├─ разговор: Claude Sonnet 5.5 + инструменты        ├─ «Меню заказов»
                      └──── ответы клиенту ──────┤  ├─ схема bot: диалоги, черновики, события           ├─ заказ клиента + журнал
                                                 │  └─ Telegram: карточки с кнопками                     └─ планшет кассы, бэк-офис, план кухни
                                                 └─ раз в 10 с: журнал изменений заказов «с номера N»
```

Код бота — папка `bot/` этого репозитория (рядом с `server/`): контракт с учётом и его тесты живут вместе.
В коде нет секретов, поэтому публикация исходников через GitHub Pages допустима (как уже с `server/`).

### Блоки бота

Каждый блок — отдельный файл со своими тестами и поддельными соседями.

| Блок | Что делает | От чего зависит |
|---|---|---|
| `uzel.ts` | приём вебхука: подпись `ts + "." + тело`, допуск 300 с, отброс повторов по `eventId`, ответ 2xx сразу; чтение текста, отправка, handoff | API «Узла» |
| `uchet.ts` | клиент `tandem_gate`: меню (кэш на минуту), создать заказ, журнал изменений, история клиента по телефону | учёт |
| `menu.ts` | окна готовности, минимум и шаг, стоп-лист, расчёт суммы и доставки — чистые функции | настройки из учёта |
| `dialog.ts` | ход разговора: история, системная часть с меню (кэш Anthropic), инструменты, проверка их ответов | `menu.ts`, модель |
| `templates.ts` | шаблоны сообщений ru/kz с номером заказа и именем | — |
| `telegram.ts` | карточки с кнопками, кто может нажимать (`/here`, `/allow` как у «Полежим?»), отметка нажавшего | Bot API |
| `watcher.ts` | опрос журнала заказов, сообщения клиенту по смене статуса, напоминания о неподтверждённых | `uchet.ts`, `templates.ts` |
| `store.ts` | схема `bot` в Postgres | — |

### Инструменты модели

`menu_search` (позиции и состав по запросу), `cart_set` (позиция и количество → проверка шага, стопа,
окна), `cart_view`, `order_details` (дата, час, доставка или самовывоз, адрес, имя), `order_summary`
(код считает сумму, доставку, проверяет минимум и возвращает готовый текст итога из шаблона),
`order_submit` (только после «да» клиента), `handoff` (причина). Модель не пишет суммы, цены и итог
своими словами — их даёт `order_summary`.

## Данные в учёте (миграция 0049)

### Меню заказов — `tandem.order_menu`

Одна строка на позицию учёта (`item_code` → `tandem.items.code`).

- `title_ru`, `title_kz`, `composition_ru`, `composition_kz`, `unit_label` («кг», «шт», «сет»);
- `price` — цена для заказов (подсказкой в разделе — цена кассы точки Енешки);
- `min_qty`, `step` (например, от 1 кг, шаг 0,5);
- `section` — «Татарские пироги», «Полуфабрикаты», «Сладкие пироги», «Выпечка», «Сеты»;
- `ready_kind`: `fresh` (печём под заказ, окно из настроек) или `stock` (с витрины или из морозилки,
  `stock_ready_minutes`, по умолчанию 120);
- `price_checked_by`, `price_checked_at` — без отметки позиции нет у бота; изменение цены снимает отметку;
- `stop_until` — «сегодня нет» до даты;
- `sort_order`, `active`.

Сеты («Чайный дастархан» 19 300 ₸) заводятся обычной позицией учёта с составом — кухня видит, что собирать.
Первичное наполнение — из закреплённых постов Instagram @eneshka.tmr (DYubWoJApkj, DYryhmTguAI,
DZXfAa1C7Wj); цены сверяет Светлана или Андрей отметкой в разделе.

### Заказ клиента — `tandem.client_orders`, `tandem.client_order_lines`

`client_orders`: `id`, `no` (номер в пределах дня), `point_id` (точка выдачи, по умолчанию `eneshka`),
`channel` (`whatsapp`), `uzel_dialog_id`, `client_phone`, `client_name`, `lang` (`ru`/`kz`),
`kind` (`delivery`/`pickup`), `address`, `for_date`, `ready_by` (час), `total`, `delivery_fee` (0 при
сумме от минимума), `prepay_required`, `pay_kind`, `courier`, `status`, `reason`, `check_uid`,
`created_at`, `updated_at`, `confirmed_by`, `confirmed_at`.

`client_order_lines`: `order_id`, `item_code`, `title` (снимок названия), `qty`, `price` (цена меню
на момент заказа), `sum`.

### Статусы

```
новый ─► подтверждён ─► готовится ─► собран ─┬─ доставка:  передан курьеру ─► в пути ─► доставлен (= чек)
   │  └─► ждёт предоплаты ─► оплачен ─┘      └─ самовывоз: ждёт клиента ─────────────► выдан (= чек)
   └─► отказ        до «доставлен/выдан» ─► отменён     после «собран» ─► не забрали / не доставлено
```

Коды: `new`, `awaiting_prepay`, `paid`, `confirmed`, `cooking`, `assembled`, `handed_to_courier`,
`on_the_way`, `delivered`, `awaiting_pickup`, `issued`, `rejected`, `cancelled`, `not_collected`.
Сервер проверяет переход по таблице разрешённых переходов; запретный переход — ошибка, а не тихий пропуск.
Причина обязательна у `rejected`, `cancelled`, `not_collected`; курьер — у `handed_to_courier`.

Кто ставит: продавец — подтверждение, отказ, предоплату; кухня и продавец — до `assembled`;
продавец или курьер — дальше (планшет или кнопки Telegram «Передал курьеру», «В пути», «Доставлено»).

Клиенту бот пишет только при `confirmed`, `awaiting_prepay`, `paid`, `on_the_way`, `awaiting_pickup`,
`rejected`, `cancelled`. Остальные статусы — внутренние.

### Журнал — `tandem.client_order_events`

`id bigserial`, `order_id`, `at`, `status_from`, `status_to`, `by_name`, `by_kind`
(`bot`/`point`/`office`/`telegram`), `payload`. Пишется в той же транзакции, что и смена статуса.
Бот читает «события с номером больше N» и запоминает N у себя — ни одно изменение не теряется
и не обрабатывается дважды.

### Кухня

- `tandem.orders_report` получает колонку «Клиенты»: сумма строк заказов клиентов на дату в статусах
  от `confirmed`/`paid` до выдачи, по позициям.
- `tandem.orders_make_docs` включает их в акт производства на склад кухни.
- Заказы, подтверждённые после создания документов на дату, показываются отдельной строкой
  «после акта»; кнопка «Дополнительный акт» создаёт акт только на них.
- Живой список «Заказы на сегодня» (бэк-офис «Склад → Заявки» и вкладка планшета): по `ready_by`,
  с составом каждого заказа и отметкой «собран».

### Выдача и касса

«Доставлен»/«Выдан» + способ оплаты вызывает `check_save` от имени точки выдачи с `uid` заказа
(идемпотентно) и ценами строк заказа; в `check_uid` заказа пишется ссылка. Если точка ещё не в режиме
кассы (`mode <> 'checks'`, у Енешки до 1.11.2026), заказ закрывается без чека и попадает в дневной отчёт
как обычно — это видно в заказе пометкой «без чека».

### Доступы (`tandem_gate`)

- **Бот — служебный ключ** (`payload.service_key`, `settings.service_key_hash`), новые действия
  в `v_service`: `bot_menu`, `bot_order_create`, `bot_order_events` (с номера N), `bot_order_get`,
  `bot_client_history` (последние адреса по телефону), `bot_order_status` (только переходы, которые
  бот вправе сделать: `cancelled` по просьбе клиента до `cooking`). Список действий добавляется
  и в `tools/office-smoke.mjs` (`SERVICE`).
- **Планшет — действия точки по коду**: `client_orders_list`, `client_order_confirm`
  (с предоплатой или без), `client_order_edit` (строки, дата, час, адрес — до `cooking`),
  `client_order_reject`, `client_order_status`. Счётчик неверных кодов `tandem_gate` действует.
- **Telegram-кнопки** идут через бота служебными действиями `bot_card_*` с именем нажавшего
  из списка допущенных; права на кнопки проверяет бот, переход — учёт.
- **Бэк-офис**: раздел «Меню заказов» (owner, admin, technologist), список заказов клиентов
  (owner, admin, accountant — чтение).
- Телефоны и адреса — персональные данные: хранятся только в учёте и в переписке «Узла»,
  в журналах бота маскируются, в Telegram-карточке телефон виден допущенным сотрудникам.

### Настройки (`tandem.settings`)

`client_fresh_cutoff` (12:00), `client_fresh_ready` (18:00), `client_fresh_next_day` (на завтра, если
позже отсечки), `stock_ready_minutes` (120), `client_min_order` (7 000 — предложение, не утверждено; доставка только бесплатная, ниже минимума — только самовывоз),
`client_hours_from`/`client_hours_to` (часы приёма), `client_pickup_points` (по умолчанию `eneshka`),
`client_prepay_rule` (`off` / `fresh` / `from_sum:N`), `client_confirm_remind_min` (15),
`client_confirm_client_notice_min` (30), `kaspi_details_ru`/`kaspi_details_kz`, `couriers` (список имён).

## Разговор

- Бот отвечает на языке клиента; шаблоны ключевых фраз — `templates.ts`, тексты сверены платной моделью
  на казахском до запуска.
- Постоянного клиента бот узнаёт по номеру и предлагает прошлый адрес.
- Перед отправкой продавцу бот всегда показывает итог («Проверьте: … Итого 9 300 ₸, доставка бесплатно,
  завтра к 18:00, ул. … Всё верно?»). Только после «да» — `order_submit` и «передал продавцу, подтвердим
  в течение 15 минут».
- В шаблонах статусов есть номер заказа и имя, поэтому тексты разные и не попадают под правило «Узла»
  «один текст — не больше 5 клиентам в час». Задержанное сообщение (`held`) бот перефразирует.

### Сценарии MVP

1. **Пирог к дате** — проверка окна свежей выпечки (до 12:00 — к 18:00, позже — на завтра), начинка,
   вес, дата и час, способ получения, итог.
2. **Полуфабрикаты сегодня** — позиции `stock`, готовность через `stock_ready_minutes` в часы приёма;
   позиция на стопе — «сегодня нет» и похожая из того же раздела.
3. **Сет** — позиция меню с составом, дальше как пирог.
4. **Вопрос о составе, цене, часах, адресе** — ответ из меню и настроек; чего там нет — «уточню
   у продавца» и handoff.
5. **Самовывоз** — точки из `client_pickup_points`.
6. **Жалоба** — извинение и сразу handoff с причиной «жалоба», без обещаний.

### Пограничные случаи

- Нерабочее время: заказ принимается, ответ «подтвердим утром с <client_hours_from>», карточка ждёт.
- Не подтверждено за `client_confirm_remind_min` в рабочее время — напоминание в Telegram;
  за `client_confirm_client_notice_min` — клиенту «продавец скоро ответит».
- Правка после подтверждения, голосовое, фото, «позовите человека», сложный казахский — handoff.
- После ответа продавца бот молчит, пока сотрудник не вернёт разговор боту в окне «Узла».

## Ошибки

- Повтор вебхука — отбрасывается по `eventId`; ответ привязан к входящему сообщению, двойного ответа
  на одно сообщение нет.
- Модель недоступна или инструмент не прошёл проверку — один повтор, затем handoff «бот не справился».
- Учёт недоступен — черновик ждёт в схеме `bot`, повторы с нарастающей паузой, тревога в Telegram;
  клиенту «заказ записан, подтвердим чуть позже».
- Telegram недоступен — карточка всё равно на планшете.
- Цена меню изменилась во время оформления — `order_summary` пересчитывает перед `order_submit`,
  об изменении суммы бот говорит клиенту.
- Секреты (`ANTHROPIC_API_KEY`, ключ «Узла» и `whsec_`, `UCHET_SERVICE_KEY`, `TELEGRAM_BOT_TOKEN`,
  `TELEGRAM_WEBHOOK_SECRET`) — только в переменных окружения контейнера на VPS.

## Проверки

1. **Учёт** — `tools/office-smoke.mjs`: меню (сверка, стоп, снятие отметки при смене цены), создание
   заказа, каждый разрешённый и пример запретного перехода, журнал «с номера N», колонка «Клиенты»
   и дополнительный акт, «выдан» → чек, доступы (бот без ключа — отказ, чужая точка — отказ).
   Весь набор до правки и после.
2. **Бот** — `deno test` с поддельными «Узлом», учётом, Telegram и моделью: подпись и повторы,
   окна готовности, сумма и минимум, стоп-лист, сценарии 1–6, handoff и молчание после ответа продавца,
   наблюдатель статусов, напоминания.
3. **Эталонные разговоры** — 30 записанных разговоров (русский и казахский) на настоящей Sonnet 5.5,
   около $2 за прогон: собранный заказ сравнивается с эталоном полями, лишнего быть не должно.
4. **Сквозная проба на стенде** — тестовый номер в «Узле», учебная точка учёта: заказ из WhatsApp,
   подтверждение на планшете и в Telegram, все статусы до «выдан», чек.

5. **Замер памяти на VPS Basic-1** — нагрузка часа пика (20 одновременных разговоров и работа кассы):
   не больше 80 % памяти, swap не используется постоянно; иначе — смена тарифа на Basic-2.

**«Готово» для MVP:** проверки 1–5 зелёные, 30 из 30 эталонных заказов собраны верно, сквозная проба
прошла, цены меню сверены. Затем запуск на боевом номере; первые две недели каждый заказ подтверждает
человек (так и задумано в MVP), по итогам — разбор журнала.
