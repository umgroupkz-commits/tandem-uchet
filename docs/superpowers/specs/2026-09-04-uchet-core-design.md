# Учёт Тандема: собственная система вместо iiko. Архитектура и подпроект «Ядро»

Дата: 4 сентября 2026. Статус: утверждено к реализации.

## 1. Зачем и в каких границах

Сеть общепита ведёт складской и производственный учёт в iiko. Запись в iiko через
облачное API на их сервере не работает (проверено 04.09.2026), лицензия дорогая,
а нужен учёт «под себя». Решение: развивать существующую программу учёта
(Supabase + GitHub Pages) до полноценного внутреннего учёта, который заменит iiko.

Что система делает:
- справочники: номенклатура, группы, единицы, склады, контрагенты, точки, пользователи;
- документы: приход, перемещение, списание, производство, инвентаризация, продажа;
- расчётные остатки по складам, себестоимость, недостачи по инвентаризациям;
- техкарты с потерями и вложенными полуфабрикатами;
- деньги: ДДС, взаиморасчёты, P&L по точкам;
- отчёты и дашборд собственницы; доступ к отчётным данным по API для аналитики.

Чего система не делает (сознательно):
- не пробивает чеки и не фискализирует — чеки идут отдельным устройством и с учётом
  не связаны;
- не ведёт остатки «в реальном времени» по каждой продаже: остаток расчётный,
  контроль — инвентаризацией (уровень «контрольный склад»);
- фабрика Актау пока не ведётся внутри: её продажи импортируются файлом, отгрузки
  в сеть — как внутренний поставщик. Схема допускает перевод Актау на полный учёт
  без переделки (Актау станет точкой со своими складами и производством).

Сроки не давят: iiko остаётся, пока новая система не будет проверена на
параллельном учёте.

## 2. Разбиение на подпроекты

Каждый подпроект — своя спецификация, план и проверка; каждый полезен сам по себе.

| № | Подпроект | Что даёт |
|---|-----------|----------|
| 1 | **Ядро** (эта спецификация) | справочники, роли, бэк-офис, перенос данных из iiko |
| 2 | Техкарты и себестоимость | редактор карт, потери, вложенность, версии по датам, себестоимость блюд |
| 3 | Документы склада | накладные, перемещения, списания, производство, инвентаризация; движения и остатки |
| 4 | Продажи как документы | нынешние отчёты точек порождают движения; расчётный расход сырья со склада точки |
| 5 | Финансы | ДДС, кассы и счета, оплаты поставщикам, взаиморасчёты, P&L по точкам |
| 6 | Отчёты и API для аналитики | отчётные представления, read-only ключ, дашборд поверх них |

Порядок именно такой: без справочников нет документов, без документов нет остатков,
без остатков финансы считают только деньги.

## 3. Архитектура всей системы

### 3.1 Где что живёт

- **Данные и логика** — Supabase, проект `qeehxcnnuzuwskznhdyg`, схема `tandem`.
  Доступ только через SECURITY DEFINER RPC (`public.tandem_api(action, payload)` и
  вспомогательные), выполнять их может только service_role, RLS на таблицах —
  запрет всего. Наружу смотрит Edge Function `uchet` — JSON-прокси к RPC.
- **Экраны** — GitHub Pages (`umgroupkz-commits/tandem-uchet`): `index.html` (точки,
  водитель, дашборд), `learn.html` (тренажёр), новый **`office.html`** (бэк-офис).
- **Фронт без сборщика**, но модульный: ES-модули в `js/` (`api.js` — вызовы,
  `auth.js` — сессия, `office/nomenclature.js`, `office/stores.js` и т.д.). Pages
  отдаёт модули как есть. Существующий `app.js` (51 КБ) не переписывается разом:
  новые экраны сразу пишутся модулями, общие куски (поиск, API-вызов) выносятся
  из `app.js` по мере надобности. Версия против кэша — `?v=N` на каждом модуле
  через одну константу сборки.

### 3.1а Переносимость на собственный сервер

Система должна переезжать на виртуальный сервер клиента без переписывания.
Отсюда правила, обязательные для всех подпроектов:

- вся логика — в SQL-функциях обычного PostgreSQL; из расширений только те, что
  есть в любом Postgres (`pgcrypto`, `uuid-ossp`); никаких функций, доступных лишь
  в Supabase;
- Edge Function `uchet` остаётся тонким прокси «JSON → RPC» без собственной логики,
  чтобы на своём сервере заменяться небольшим сервисом на Node;
- не используем Supabase Auth, Storage и Realtime — они и есть привязка к платформе;
  вход свой (таблица сессий), файлов не храним;
- экраны — статические файлы, которым всё равно, кто их отдаёт: GitHub Pages
  сейчас, nginx на сервере клиента потом.

Переезд тогда сводится к `pg_dump` → восстановление, запуску прокси и nginx,
домену, HTTPS и резервному копированию — работа администратора, а не разработчика.

### 3.2 Три слоя данных

1. **Справочники** — номенклатура с деревом групп и типом позиции, единицы, склады
   (каждый привязан к точке), контрагенты, точки, пользователи.
2. **Документы** — одна таблица `documents` (тип, номер, дата, статус
   черновик/проведён, склад-откуда, склад-куда, контрагент, автор, комментарий) и
   `document_lines` (позиция, количество, единица, цена, сумма). Типы: `invoice_in`
   (приход), `transfer`, `writeoff`, `production`, `inventory`, `sale`. Нынешние
   `daily_reports` + `sale_lines` + `takeout_lines` сохраняются и в подпроекте 4
   получают зеркало-документ типа `sale`.
3. **Движения** — `stock_moves` (документ, склад, позиция, количество со знаком,
   себестоимость единицы, дата). Порождаются только проведением документа. Остаток
   на дату по складу и позиции = сумма количеств. Инвентаризация сравнивает факт с
   расчётом и записывает корректирующее движение — так недостачи получают цену.

### 3.3 Проведение и отмена

Проведение — одна транзакция в RPC: проверить документ (склады, позиции активны,
количества > 0, права роли), породить движения, поставить статус и время. Отмена
проведения удаляет движения; запрещена, если по затронутому складу есть проведённая
инвентаризация с более поздней датой. Правка проведённого документа = отмена → правка →
проведение.

### 3.4 Себестоимость

Товары — средневзвешенная по складу с приходов (пересчёт при каждом приходе).
Блюда и полуфабрикаты — по действующей на дату техкарте с учётом потерь и вложенных
полуфабрикатов. Детали — спецификация подпроекта 2.

### 3.5 Роли и доступ

Точки, водитель и собственница входят как сейчас (коды). Бэк-офис — именованные
пользователи (логин + PIN) с ролью:

| Роль | Что видит и делает |
|------|--------------------|
| `admin` | всё, включая пользователей и настройки |
| `owner` (собственница) | все справочники и отчёты, правка цен и справочников, документы — просмотр |
| `accountant` | контрагенты, приходные накладные, финансы |
| `technologist` | номенклатура, техкарты, акты производства |
| `storekeeper` | приём, перемещения, списания, инвентаризации |

Матрица «роль → раздел → действие» лежит в базе (`role_permissions`), проверяется в
RPC на каждом действии, а фронт по ней же прячет разделы. Один пользователь — одна
роль; кому нужно больше, тому `admin`.

Для аналитики (Андрей) — отдельный read-only ключ к отчётным представлениям
(подпроект 6).

## 4. Подпроект 1 — «Ядро»

### 4.1 Что входит

1. Схема справочников и пользователей (миграции SQL).
2. Перенос данных из iiko скриптом из уже выгруженных файлов.
3. `office.html` с разделами Номенклатура, Склады, Контрагенты, Пользователи.
4. RPC-действия для всего перечисленного с проверкой прав.
5. Права по ролям.

Не входит: документы, движения, редактор техкарт, финансы, тренажёр бэк-офиса
(тренажёр дополняется по мере появления разделов, отдельной задачей).

### 4.2 Модель данных

Существующие таблицы сохраняются; `items` расширяется, не пересоздаётся —
на ней держатся экраны точек.

```
item_groups   id uuid PK, parent_id uuid null → item_groups, name text,
              sort_order int, active bool, iiko_id uuid unique null
units         id text PK ('шт','кг','л','порц' …), name text, precision int
items (+)     group_id uuid → item_groups, unit_id text → units,
              item_type text ('goods'|'dish'|'prepared'|'service'),
              iiko_id uuid unique null,
              for_sale bool -- показывать на экранах точек; у всех нынешних позиций true,
                            -- у переносимого сырья false. Фильтр в действии items
                            -- включается ДО переноса, иначе точки увидят 1 600 строк сырья
              -- старые колонки category/group_name/unit остаются как есть
              -- до переезда экранов точек на group_id/unit_id
stores        id uuid PK, name text, point_id text null → points,
              organization_id uuid null (из iiko), active bool,
              sort_order int, iiko_id uuid unique null
points (+)    default_store_id uuid null → stores
counteragents id uuid PK, name text, kind text ('supplier'|'customer'|'employee'|'other'),
              bin text null, phone text null, note text, active bool,
              iiko_id uuid unique null
users         id uuid PK, login text unique, name text, role text,
              pin_hash text, active bool, created_at,
              must_change_pin bool,   -- временный PIN не сменён: доступны только me/logout/change_pin
              failed_attempts int,    -- неверных попыток входа подряд
              locked_until timestamptz -- до этого момента вход запрещён (5 попыток → 15 минут)
sessions      token text PK, user_id uuid → users, created_at, expires_at
role_permissions role text, section text, action text ('view'|'edit'), PK(role,section,action)
```

Ключ идемпотентности переноса — `iiko_id`. Для позиций, уже загруженных ранее
(`items.iiko_code`), при переносе сначала ищется совпадение по `iiko_code`, и строка
дополняется, а не дублируется.

`realization_clients` (клиенты реализации) остаются отдельной таблицей: в
подпроекте 5 они станут контрагентами вида `customer`, сейчас трогать незачем.

### 4.3 Перенос из iiko

Скрипт `tools/iiko-migrate.mjs` читает файлы выгрузки (группы, позиции, склады,
контрагенты; единицы измерения дотягивает живым вызовом `measure_units/list` — это
чтение, оно работает) и шлёт пачками в RPC `tandem_migrate(kind, rows)`.
Повторный запуск обновляет по `iiko_id`, не дублирует. Удалённые в iiko записи
переносятся с `active=false` — чтобы старые документы не потеряли ссылки.

Ожидаемые объёмы: 114 групп, 3 726 позиций, 27 складов, 271 контрагент. Скрипт
печатает счётчики «в файле / вставлено / обновлено / пропущено», и они обязаны
сойтись.

Привязка складов к точкам делается руками в бэк-офисе после переноса (в iiko
её нет — там организации, а не точки). Пока склад не привязан, он виден в списке
с пометкой «без точки».

### 4.4 Вход и сессии

RPC `office_login(login, pin)` → проверка `pin_hash` (bcrypt через `pgcrypto`),
запись в `sessions` (срок 12 часов), возврат токена и роли. Все действия бэк-офиса
несут `token`; RPC ищет сессию, роль и разрешение в `role_permissions`; при отказе —
ошибка `forbidden`. Выход — удаление сессии. Первый администратор создаётся
миграцией с временным PIN, который меняется при первом входе.

Подбор PIN закрыт локом: пять неверных попыток подряд по одному логину ставят
`locked_until = now() + 15 минут`, и до этого срока вход возвращает `unauthorized`
«Слишком много попыток, подождите 15 минут» — даже с верным PIN. Удачный вход обнуляет
счётчик. Сравнение хэша считается всегда, в том числе когда такого логина нет: иначе
время ответа выдаёт, существует ли пользователь.

Временный PIN проверяется на сервере, а не только на экране: пока у пользователя
`must_change_pin = true`, диспетчер пропускает только `me`, `logout` и `change_pin`,
на остальное отвечает `forbidden` «Сначала смените временный PIN».

### 4.5 Экраны `office.html`

Один файл-оболочка (шапка с именем пользователя и ролью, боковое меню разделов по
правам) и модули на раздел:

- **Номенклатура** — слева дерево групп (свернуть/развернуть, счётчик позиций),
  справа список с поиском по имени и артикулу, фильтром по типу и активности.
  Карточка позиции: имя, тип, единица, группа, артикул, активна, заметка; блоки
  «цены по точкам» (`item_prices`), «фасовка» (`pack_*`), «короткий лист» (`item_rank`).
  Создание позиции, перенос в другую группу, деактивация (удаления нет). Группы:
  создать, переименовать, переместить.
- **Склады** — список, привязка к точке, активность, склад по умолчанию точки.
- **Контрагенты** — список с поиском и фильтром по виду, карточка, создание,
  деактивация.
- **Пользователи** (только `admin`) — список, создание, роль, сброс PIN, деактивация.

Все списки грузятся страницами по 200 с поиском на сервере — номенклатура на
3 700 строк целиком в браузер не тянется.

### 4.6 RPC-действия (все с `token`)

Бэк-офис идёт через отдельную RPC `public.tandem_office(action, payload)`, а не через
`tandem_api`: у той свой вход по кодам точек и 12 КБ логики экранов точек. Прокси
`uchet` направляет туда любое действие с префиксом `office_`. `tandem_office` —
диспетчер: проверяет сессию, выводит раздел и требуемое право из имени действия и
вызывает функцию раздела `tandem.office_nomenclature / office_stores /
office_counteragents / office_users`.

`office_login`, `office_logout`, `office_me`, `office_change_pin`;
`groups_list`, `group_save`; `items_search {q, group_id, type, active, page}`,
`item_get`, `item_save`, `item_prices_save`; `stores_list`, `store_save`;
`counteragents_list {q, kind, page}`, `counteragent_save`;
`users_list`, `user_save`, `user_reset_pin`.

Без токена, мимо диспетчера, идут два служебных RPC (только `service_role`, защита —
код собственника из `tandem.settings.owner_pin`): `tandem_migrate(p_pin, kind, rows)` —
перенос справочников из iiko, вызывается скриптом `tools/iiko-migrate.mjs`;
`tandem_test_cleanup(p_pin)` — уборка записей `ZZ_TEST_*` и пользователей `zz_test_*`
после дымового теста, возвращает `{ok, deleted:{...}, leftovers}`.

Функции разделов `tandem.office_*` — `security invoker` и без прав у `PUBLIC`,
`anon`, `authenticated`: их зовёт только диспетчер `public.tandem_office`, который
сам `security definer`.

Ошибки — единый формат `{error: код, message: текст по-русски}`; фронт показывает
текст, коды (`forbidden`, `not_found`, `validation`) нужны для тестов.

### 4.7 Проверка

- Перенос: счётчики скрипта совпадают с файлами; SQL-контроль — нет позиций без
  группы и без единицы, `iiko_id` уникален, число активных совпадает с iiko.
- RPC: скрипт `tools/office-smoke.mjs` — вход, создание тестовой позиции/склада/
  контрагента с префиксом `ZZ_TEST_`, чтение, правка, деактивация, попытка
  запрещённого действия под ролью `storekeeper` (ждём `forbidden`), выход; после
  прогона тестовые записи удаляются SQL-ом и это проверяется.
- Экраны: живой прогон в браузере по каждому разделу под двумя ролями.
- Экраны точек: после переноса поиск, плитки и короткие листы работают как раньше
  (регресс — тот же набор действий, что в тренажёре).

### 4.8 Что считаем готовым

Подпроект закрыт, когда: данные из iiko перенесены и сверены по счётчикам;
администратор, бухгалтер, технолог и кладовщик могут войти и видят только своё;
номенклатуру, склады и контрагентов можно вести без iiko; экраны точек не
изменили поведения. После этого пишется спецификация подпроекта 2.
