# Тандем KZ — учёт продаж и денег (прототип)

Статическая страница (`index.html` + `app.js`) для GitHub Pages.
API — edge-функция Supabase `uchet` (`https://qeehxcnnuzuwskznhdyg.supabase.co/functions/v1/uchet`), POST `{action, payload}`.

Почему страница здесь, а не в Supabase: на домене `*.supabase.co` и Edge Functions, и Storage
переписывают `text/html` в `text/plain` и ставят CSP `sandbox` — HTML там не отдать
(https://supabase.com/docs/guides/functions/http-methods). Функция на GET делает редирект сюда.

Публикация: коммит в `main` → GitHub Pages обновляет страницу за 1–2 минуты.

## Бэк-офис (`office.html`)

Справочники: номенклатура с группами, склады, контрагенты, пользователи. Вход — логин и PIN,
роли: администратор, собственник, бухгалтер, технолог, кладовщик (права — таблица
`tandem.role_permissions`). Логика — RPC `tandem_office` (диспетчер) и функции
`tandem.office_*`; файлы миграций — `db/migrations/`.

Вход защищён: пять неверных PIN подряд запирают логин на 15 минут, а пока пользователь
не сменил временный PIN, ему доступны только `me`, `logout` и `change_pin`.

Дымовой тест: `node tools/office-smoke.mjs all` (нужен `TANDEM_ADMIN_PIN`; с
`TANDEM_OWNER_PIN` дополнительно идут разделы переноса и в конце — уборка). Тест заводит
записи `ZZ_TEST_*` и пользователей `zz_test_*` и сам их убирает действием `test_cleanup`
(RPC `public.tandem_test_cleanup`, защита — код собственника); последняя проверка прогона
подтверждает, что следов не осталось. Без `TANDEM_OWNER_PIN` уборка не выполняется —
записи придётся снести вручную.

Перенос справочников из iiko: `node tools/iiko-migrate.mjs` (см. шапку скрипта).
**Повторный перенос обновляет только позиции, не правленные в бэк-офисе** (правка ставит
`items.source='office'`, и такая строка при переносе пропускается). А вот названия
групп, складов и контрагентов, изменённые в офисе, перенос перезапишет.

Техкарты: раздел `office.html` → Техкарты; перенос из iiko — `node tools/iiko-migrate-charts.mjs`
(около часа, в фоне, кэш в `data/iiko/charts`); себестоимость считает `tandem.item_cost`,
отчёт — `tandem.menu_foodcost`; порог фудкоста — `settings.foodcost_alert`.

## Склад (`office.html` → Склад)

Пять типов документов: приход, перемещение, списание, акт производства, инвентаризация.
Кто проводит какой тип:

- **кладовщик** — приход, перемещение, списание, инвентаризация;
- **бухгалтер** — приход;
- **технолог** — производство;
- **собственница и администратор** — все типы без ограничений.

Стартовые остатки склада задаются его первой инвентаризацией: до неё склад живёт с
расчётным остатком от нуля, документ фиксирует фактическое количество как есть.
Отрицательный остаток допускается — проведение возвращает предупреждение, интерфейс просит
подтвердить, но не блокирует. Отменить проведение документа нельзя, если после него по
любому из его складов уже проведена инвентаризация (она фиксирует момент; более ранний
документ отменить — значит исказить то, что инвентаризация уже подтвердила).

**Стартовые остатки из iiko.** В форме инвентаризации есть кнопка «Загрузить факт из
файла»: она читает Excel-выгрузку остатков и проставляет фактическое количество, не сохраняя
и не проводя документ. Порядок перехода на свой учёт в день X такой:

1. в iiko выгрузить «Расширенную оборотно-сальдовую ведомость» **по одному складу** за период,
   заканчивающийся днём старта (сводный отчёт по нескольким складам не годится: остатки в нём
   сложены, разложить обратно нечем — загрузка такой файл отклоняет и просит выгрузить по
   одному складу);
2. в бэк-офисе создать инвентаризацию на этот склад и нажать «Загрузить факт из файла» —
   берётся колонка «Кол-во» из группы «Остатки на конец»; строки с нулём и без количества
   пропускаются, о чём написано в сводке;
3. проверить список «не найдено в номенклатуре» под таблицей: это позиции, которых в
   справочнике нет или названия расходятся — их нужно завести или добавить псевдоним и
   загрузить файл заново;
4. провести документ — с этого момента склад живёт своим учётом.

Подходит и произвольный лист с колонками «Наименование», «Код» и «Количество» (колонка склада,
если она есть и складов в ней несколько, спрашивается отдельно). Настоящий пересчёт с телефона
после этого корректирует остатки обычной инвентаризацией — загрузка из файла нужна один раз,
чтобы не вбивать сотни строк руками.

Пересборка остатков — RPC `stock_rebuild`, доступна только администратору: пересчитывает
всю `stock_balances` заново из `stock_moves` и возвращает число расхождений, найденных до
пересчёта (используется для сверки, в норме 0).

Дымовой тест (раздел `stock` внутри `office-smoke.mjs all`) прогоняет весь цикл на тестовых
складах и позициях `ZZ_TEST_*`: два прихода со средней, перемещение, списание, производство
по карте, уход в минус с предупреждением и отмену, инвентаризацию с недостачей, запрет
отмены прихода после инвентаризации, отмену самой инвентаризации и последующую отмену
прихода, пересборку остатков (0 расхождений) и права ролей по типам документов.

Спецификация и план — `docs/superpowers/`.

## Продажи и оборотная ведомость (`office.html` → Склад)

**Продажи** (подпроект 4, миграции 0022–0024). Отчёт точки (`tandem_api.save_report`) сам
порождает документ «Продажа» (ПД-…) на складе точки по умолчанию: блюдо с действующей на дату
отчёта техкартой списывает ингредиенты (один уровень), позиция без карты — саму себя, по средней
цене склада. Правка отчёта пересчитывает документ; руками продажу не создают, не проводят и не
удаляют. Вкладка «Продажи» показывает отчёты точек за период и их состояние; «Провести продажи за
период» (администратор, собственник, бухгалтер; до месяца) — когда склад точке привязали позже,
появилась техкарта или был сбой. Продажа не проводится, если инвентаризация склада более поздним
днём уже учла проданное (иначе двойное списание); инвентаризация в тот же день считается утренней.
Спецификация: `docs/superpowers/specs/2026-09-18-uchet-sales-design.md`.

**Оборотная ведомость** (вкладка «Ведомость», действие `stock_turnover_report`, функция
`office_stock_ext`) — аналог «Расширенной оборотно-сальдовой ведомости» iiko: остаток на начало,
приход, перемещения, производство, продажи, списания, инвентаризация, остаток на конец, суммы по
себестоимости движений; выгрузка в CSV. Новые отчёты склада добавляются в `office_stock_ext`.

Дымовой тест работает на служебной выключенной точке `zz_test` — настоящие точки не трогает.

**Готовность** (вкладка «Готовность», действие `stock_quality_report`, функция `tandem.quality_report`, миграция 0028) —
девять проверок того, что мешает учёту: сырьё без цены (с числом карт, которые оно блокирует), блюда на
продаже без техкарты, позиции без цены, дубли названий, позиции без группы, точки без склада,
непроведённые продажи, минусовые остатки, пользователи. Клик по строке открывает карточку позиции
(`#item/<код>`) или техкарту.

## Склад с телефона (`stock.html`)

Отдельная лёгкая страница для кладовщика на телефоне — без бэк-офисной шапки и меню.
Вход тот же, что и в бэк-офисе: логин и PIN, те же учётные записи и роли. Склад выбирается
один раз и запоминается в `localStorage` на устройстве; сменить его можно кнопкой в шапке.

**Склады пользователя** (миграция 0021, таблица `tandem.user_stores`). В карточке пользователя
бэк-офиса склады отмечаются галочками. Ни одной галочки — пользователь работает со всеми
складами (администратор, собственник, бухгалтер). С галочками сервер пускает только к своим:
«свой» склад документа (приход — получатель, прочие — источник) должен быть закреплён, журнал и
карточка показывают документы, касающиеся его складов, остатки и движения — только его склады.
Перемещать можно на любой склад. На телефоне выбор склада показывает только закреплённые, а
единственный закреплённый выбирается сам.

Четыре сценария, доступность каждого — по правам роли на тип документа:

- **приёмка** — нужно `doc:invoice_in:edit`;
- **инвентаризация** — нужно `doc:inventory:edit`;
- **перемещение** — нужно `doc:transfer:edit`.
- **списание** — нужно `doc:writeoff:edit`; причина (порча, проработка, питание персонала, прочее), предпросмотр остатков перед проведением.

Черновик каждого сценария живёт в `localStorage` браузера телефона (ключ по сценарию и складу)
и переживает закрытие вкладки. Инвентаризация дополнительно хранит `server_id` черновика,
сохранённого на сервере (`doc_save`): при «Назад к вводу» серверный черновик не создаётся
заново, а переиспользуется тем же документом. Частые позиции в приёмке и перемещении
предлагаются по остаткам склада (`stock_balances`, включая нулевые), а не по последним
приходам — так в список попадает то, что на складе действительно числится.

Инвентаризация — «слепая»: остатки системы не показываются во время пересчёта, посчитанное
количество вводится с чистого листа. Перед проведением — сводка расхождений (что и на сколько
разошлось) для проверки кладовщиком. Уход в минус (при перемещении) подтверждается обычным
диалогом браузера (`confirm`), проведение не блокируется.

Экран смены временного PIN есть и здесь — не только в бэк-офисе: пользователю с временным
PIN сразу после входа предлагается задать свой.

Ссылки: из бэк-офиса на телефонную версию — кнопка «Телефон» в шапке; из телефонной версии
назад на страницу отчёта точки — ссылка на экране входа.

## Маршрут проверки (`guide.html`)

Страница для тестирования программы людьми клиента: 29 шагов по разделам (подготовка,
кладовщик с телефона, документы и остатки, техкарты и производство, продажи с учебной точки, вход и защита, загрузка
остатков iiko). У каждого шага — где, что сделать и что должно получиться; отметки
«Получилось / Не так» с комментарием хранятся в `localStorage`, внизу — текст отчёта, который
копируется или уходит в WhatsApp. Все шаги идут на учебных складах, настоящие не затрагиваются.
Ожидаемые цифры (средняя 525, себестоимость карты 720, полуфабрикат 630) проверены прогоном
маршрута через RPC. Ссылка — «Маршрут проверки» в шапке бэк-офиса.

## Вход по кодам и служебный ключ (миграции 0029–0030)

Все запросы с сайта идут через одну функцию базы `public.tandem_gate` — прокси (Edge Function и
`server/proxy.mjs`) только передают ей действие. Она:

- считает неверные коды точек, собственника и водителя: 10 за 5 минут по одной точке (или по входу без
  точки) либо 60 по всем — и вход по кодам закрывается на 5 минут, в том числе для верного кода;
- служебные действия (`migrate`, `test_cleanup`, `sync_*`, `recalc_ranks`, `set_*`) пускает только с
  длинным ключом `service_key` (в базе — его sha256 в `settings.service_key_hash`); кода собственника для
  них больше недостаточно. Ключ лежит вне репозитория (`data/service_key.txt`), скриптам передаётся
  переменной `TANDEM_SERVICE_KEY`;
- смена своего PIN в бэк-офисе закрывает остальные сессии пользователя, текущая остаётся.

## Прейскурант iiko (`tools/load-pricelist.mjs`)

Цены продажи штучных товаров в iiko заданы прейскурантом по подразделениям и через API не отдаются
(проверено 19.09.2026: меню приходит пустым, ценовые категории ключу закрыты). Источник цен — отчёт iiko
«Сводный прейскурант» в Excel: `node tools/load-pricelist.mjs "<файл.xlsx>"` (нужен `TANDEM_SERVICE_KEY`,
`--dry` — только разбор). Цены ложатся в `item_prices` по артикулу; соответствие подразделений точкам — в
начале скрипта. Себестоимость из того же файла ставится товарам без учётной цены (`migrate/costs`).
Миграция 0031 выставляет на продажу товары, у которых есть цена на настоящей точке, и добавляет их группы
в ассортимент этих точек. Загружено 19.09.2026 из прейскуранта от 21.08.2026.

## Касса: продажи в течение дня (миграция 0033)

Пятый режим точки — `checks`. Страница `kassa.html` (планшет у прилавка, на телефоне чек уезжает в нижнюю
панель): продавец нажимает позиции, выбирает оплату — наличные, Kaspi QR, перевод или карта — и чек пробит.

- Чек — первичка (`tandem.checks`, `tandem.check_lines`). После каждого чека сервер пересобирает из чеков
  деньги по каналам и строки продаж дневного отчёта (`tandem.check_rollup`) и тут же проводит складской документ
  «Продажа» (`tandem.sale_sync`). Склад, вкладка «Продажи» бэк-офиса и сводка собственника обновляются с каждым
  чеком, а не вечером.
- Связь: чек сначала кладётся в очередь планшета (localStorage) и досылается в фоне; сервер узнаёт досылку по
  `uid` и второй чек не создаёт. Вход без связи — только на том же планшете с тем же кодом.
- Исправление — тот же `uid` с новым составом; отмена — `check_void` с причиной. Цена строки правится (скидка),
  цена прейскуранта и название берутся из базы. Сырьё (не «в продаже») пробить нельзя.
- Закрытие смены — обычная форма дневного отчёта (`index.html`): у кассы поля выручки только для чтения, продавец
  вводит пересчёт наличных, расходы и сверку. Присланные формой деньги и продажи сервер не берёт — только из чеков.
  До закрытия смены отчёт кассы числится в сводке как «не сдан».
- Канал «карта» (`daily_reports.card`) добавлен всем точкам: форма отчёта, сводка, CSV, список продаж бэк-офиса.
- Режим точки меняется в базе: `update tandem.points set mode = 'checks' where id = '…'`. Точки: `ucheb_kassa`
  («Учебная касса», для маршрута проверки) и `zz_kassa` (служебная, выключена, для дымового теста).

## Расход для 1С (миграция 0034)

Склад → вкладка «Расход для 1С»: сколько продуктов ушло на проданное за период — в позициях, кодах и
единицах 1С. Это основа акта списания «на основании продаж», которого требует бухгалтер. Берётся расход
проведённых продаж и актов производства, кроме полуфабрикатов (1С знает сырьё, из которого они сделаны).

- Справочник позиций 1С — `tandem.catalog_1c` (из материальной ведомости 1С); у позиции учёта — `code_1c` и
  `k_1c` (сколько единиц 1С в одной нашей: пакетик кофе = 0,04 блока по 25).
- Соответствие меняется там же, в окне «Указать позицию 1С» (право `doc:sale:edit` — бухгалтер, собственник,
  администратор). Справочник и соответствия пачкой — действие `stock_1c_catalog_save`.
- Первая загрузка — из сверки апреля 2026: 294 позиции 1С, 193 соответствия (данные клиента вне репозитория).

## Точки в бэк-офисе (миграция 0035)

«Склады» → таблица «Точки продаж»: как точка сдаёт продажи (касса, позиции, заборный лист, файл, суммы), юрлицо,
код входа (задаётся заново, текущий не показывается; код собственника, водителя или другой точки не принимается),
группы меню на экране точки, работает ли точка. Права — как у складов (`stores:edit`: собственник, администратор).

## Полное ревью проекта (миграции 0041–0043, сборка 20)

Восемь независимых ревьюеров прошли весь проект, каждую находку перепроверили три скептика: 80 подтверждённых
(около 60 уникальных). После исправлений — второе независимое ревью самих исправлений (26 замечаний, 23
подтверждены) и второй круг правок. Всё — в трёх миграциях и во всех экранах.

- **Склад (0041).** В `stock_balances` хранится стоимость остатка `value` — всегда равна сумме движений. Приход на
  минус сначала переоценивает остаток отдельной строкой `stock_moves.adj` (в оборотке — «Переоценка», в «Прибыли по
  точкам» входит в себестоимость), средняя = цена прихода: деньги не теряются и средняя не скачет. Инвентаризация
  считает остаток «на конец дня» из уже проведённого и не стирает документы более поздних дат; документ датой раньше
  проведённой инвентаризации не проводится, а вошедший в её расчёт — не отменяется (кроме продажи: продажа кассы
  пересобирается и после инвентаризации того же дня). Полуфабрикат и блюдо из него в одном акте — в правильном
  порядке. Цена расхода без остатка — учётная, иначе по техкарте. Учётная цена не откатывается старыми и нулевыми
  накладными, отмена единственной накладной возвращает прежнюю. `doc_save` — ключ повтора `client_key` (двойной
  клик и потерянный ответ не создают второй документ), окно дат для новых документов, понятные ошибки.
- **«Готовым со склада» (0041).** `tandem.store_ready(store_id, item_code, date_from)`: на этом складе с этой даты
  позиция продаётся готовой. Строки ставит ПРОВЕДЕНИЕ документов плана заявок (склад точки, а также склад кухни, если
  он склад точки), отмена проведения их снимает; вручную — «Склад» → «Заявки» → «Что склады получают готовым».
  Изменение помечает затронутые продажи и пересобирает их частями по 5 (`stock_ready_resync`). Признак
  `items.sell_from_stock` удалён.
- **Точка, касса, вход (0042).** Отчёт точки принимает «1,5», «12 500», пустые поля; мусор — понятная ошибка, а не
  500. Название строк продаж — из справочника (XSS в сводке собственника закрыт и на сервере, и на экране). Отмена
  чека — только с причиной; правка и отмена в закрытую смену запрещены, собственник открывает смену заново
  (`reopen_shift`); отмены и исправления видны в сводке как «было → стало» (`checks.first_total`). Счётчик неверных
  кодов: ключ точки, общий замок `master` для кода собственника и водителя и порог по IP (`_ip` ставят Edge Function
  и прокси, подменить нельзя); чужие ошибки больше не запирают все точки. Смена своего PIN — с текущим PIN, у
  администратора и собственника не меньше 6 цифр. Повтор записи водителя (`uid`) не задваивает долг.
- **Номенклатура и техкарты (0043).** Переименование группы не убирает позиции с экранов точек и не открывает им
  чужие; артикул и группу можно очистить; единицу нельзя сменить у позиции с историей; дата версии карты — строго
  ГГГГ-ММ-ДД; цикл в картах ловится на весь период; перенос из iiko не закрывает карты офиса; CSV с десятичной запятой.
- **Экраны.** Бэк-офис: редактор техкарты не переставляет цифры, формы не закрываются от клика по фону и не теряются
  при истёкшей сессии (окно повторного входа), нет связи — понятное сообщение, устаревшие ответы отчётов не рисуются,
  двойное нажатие не создаёт дублей. Касса: очередь с версиями записей, правка во время отправки не теряется, смену не
  закрыть с неотправленными чеками, неотправленные и отклонённые чеки любой даты видны. Склад с телефона и заявка:
  повтор после обрыва не создаёт второй документ, кнопки не залипают, черновик заявки хранится до отправки.
- **Свой сервер.** Прокси не портит кириллицу в больших запросах, переживает обрыв соединения с базой, пароль базы со
  спецсимволами работает; копии — вне папки сайта; в seed случайные коды; README — порядок переезда без потери
  записей, восстановление из копии и выкладка функции `uchet` без проверки JWT.
- **Данные.** Цена хлеба, перенесённая из iiko за упаковку, исправлена на цену за килограмм (175 → 388,89 ₸/кг).

## Обучение (`test.html`, миграция 0048, сборка 22)

Интерактивная обучалка прямо в рабочей программе. Человек открывает `test.html` (ссылка «Обучение» в шапке
бэк-офиса), вводит **код обучения** — и видит все учебные входы сразу (логины и PIN кладовщика, бухгалтера,
технолога, собственника, коды «Учебной кассы» и «Учебной точки», учебный код сводки) с кнопками «Копировать».
Затем выбирает роль и проходит уроки по порядку: программа затемняет экран, обводит нужную кнопку или поле,
объясняет («в iiko это …, здесь …») и ждёт, пока человек нажмёт или введёт сам; «Ввести за меня» и «Назад» есть
на каждом шаге. После уроков — список «Теперь сами»: то же без подсказок. Ссылка на роль — `test.html#sklad`,
`#buh`, `#tech`, `#kassa`, `#point`, `#owner`.

- **Уроки:** 50 уроков, 680 шагов (`js/tours/<роль>.js`): кладовщик 11, бухгалтер 8, технолог 9, касса 9, точка 4,
  собственник 9. Движок — `js/tour.js` (подключён на всех рабочих страницах), формат уроков — `docs/tour-format.md`.
- **Код обучения и учебные учётки (0048).** Администратор: «Пользователи» → блок «Обучение» → код обучения →
  «Создать учебные учётки» (`uch.sklad`, `uch.buh`, `uch.tech`, `uch.owner`, случайные PIN). «Сменить код
  обучения и PIN» — старые учебные PIN перестают работать. Код хранится хэшем (`settings.training_code_hash`);
  гейт `training_info {code}` отдаёт входы, неверный код — неудача в `pin_failures` (10 за 5 минут — пауза).
- **Защита (0048).** Учебная учётка (`users.training`) пишет только туда, где ошибка ничего не портит: документы —
  если все склады учебные; новая позиция становится учебной (`items.training`), техкарты — только учебных
  позиций; справочники, цены, пользователи, склады, настройки — отказ «в обучении его только показывают»; PIN не
  меняется. Учебный код сводки (`settings.training_owner_pin`) видит и закрывает только учебные точки
  (`points.training`: «Учебная точка», «Учебная касса»). Учебные позиции не попадают в меню и техкарты настоящих точек.
- **Проверка:** `node tools/tour-run.mjs role:<роль>` — автопрогон уроков в браузере без окна (движок сам нажимает
  и вводит), учётки — `TANDEM_TRAINING_CODE` или файл `TOUR_CREDS`; `TOUR_WIDTH`/`TOUR_HEIGHT` — планшет или телефон.
  `office-smoke.mjs training` проверяет защиту на своём пользователе `zz_test_*` и код обучения не меняет.
- Уроки оставляют следы только на учебных складах и в учебной точке и кассе (приходы с комментарием «обучение»,
  учебные чеки, «Учебный ПФ фарш»). Учебные склады время от времени обнуляют инвентаризацией.
